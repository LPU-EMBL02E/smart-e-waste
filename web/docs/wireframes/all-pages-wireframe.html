About this file

  • One wireframe per page, plus the important states (errors, empty, refused, failed refresh). Links inside the frames jump to the target page, so you can click through each workflow.
  • Styled with the tokens in web/docs/DESIGN.md: white surfaces, black outlines, lavender for the main action and the focal panel.
  • Numbered dots 1 match the notes beside each frame. Turn notes off for a clean view; turn on Phone width to see every page at 390 px.
  • P28 = proposal in API_Design.md §9, not yet confirmed. Open = no answer in the docs yet. All paths are P28.
  • Names, numbers and codes are made up. No point value, rate or cap is set by the plan.
Completed server-confirmed success Pending waiting or needs attention Voided failure or reversal Read neutral

Workflow paths (click through)

  • W1 Register: G2 → G5 → email link → S2
  • W2 Sign in: G1 → S2 (student) or A1 (admin) · Log out from any shell → G1
  • W3 Admin creates accounts: A5 or A4 import → Send email → G4 → G1 · fallback A6 Set a password
  • W4 Forgot password: G1 → G3 → email → G4 → G1
  • W5 Deposit: S3 QR → bin K1 → K2 → K3 → K4 → K5 → S2 / S4 / S9
  • W6 Redeem: S6 → S7 → S8 … admin A21 Mark fulfilled → student S9
  • W7 New QR: S3 Make a new QR code
  • W8 First setup: seed admin → G3/G4 → A8 → A14 → A17 → A22
  • W9 Monitor bins: A1 → S9 alerts → A15 → A16
  • W10 Void: A10 → A11 · W11 Points rate: A22 · W12 Rewards: A18 → A19/A20
  • W13 Deactivate: A6, A9 · W14 New bin secret: A15 → A17 · W15 Stuck sessions: A1 → A12 · W16 Standings: S5, A2

Deposit sequence

  1. K1: controller ready, scanner armed.
  2. Scan → POST /device/sessions → K2 (or K7/K8 on refusal).
  3. Stable weight + camera check → K3.
  4. deposit accepted → K4; rejected → K7.
  5. Actuator, then complete → K5; unreachable → K6 and retry before the next deposit.
  6. Cancel touch or 90 s timeout → session ends, back to K1.

K7 messages are plain words, never codes. A full list is in the PDF, Appendix A.
